# PM SPEC — Core triage & digest experience

Scope: the user-facing half. Storage/model/runtime decisions are named only where the UX forces them.

---

## 1. THE SIGNAL

### Decision: a **new, explicit, two-polarity signal**. Do NOT reuse `starred`.

**Vocabulary (user-facing):** "More like this" / "Less like this". Never "like/dislike" (implies rating the article), never "keep/reject" (veille's operator vocabulary, meaningless on a phone).

**Why not star:**
1. **Star has no negative twin.** Veille's `sim = cos(liked) − cos(rejected)` (BRIEF.md:34) needs both centroids. There is no existing app affordance that means "not this". So we are building a new negative signal *no matter what*. Once the negative needs new UI + new storage, making the positive symmetric costs ~nothing and keeps the two centroids drawn from the same interaction, same intent, same moment. Asymmetric provenance (positive = save-for-later, negative = explicit rejection) would make the two centroids non-comparable and the subtraction meaningless.
2. **Star is server-synced and already load-bearing.** It's `ALL_STARRED_ITEMS(-11)` in the drawer, it round-trips to Nextcloud, it's the default right-swipe (`SP_SWIPE_RIGHT_ACTION_DEFAULT = "1"`, `SettingsActivity.java:102`). Users star to read later, to archive, to send to another device. That distribution is "things I didn't have time for", not "more of this" — it will poison the liked centroid with a systematic bias toward *long* articles.
3. Star is destructive-to-taste and irreversible: unstarring after reading is normal behaviour and would read as a retraction of a taste signal it never was.

**But do seed from star, once.** On first run of the AI feature, offer a one-tap "Use my starred articles to get started" that emits `keep` decisions for the (up to) 50 most recent starred items. Opt-in, one time, shown in the cold-start banner (§2). This solves cold start cheaply while keeping the ongoing signal clean.

### Where the user gives the signal — three surfaces, in priority order

| Surface | Positive | Negative | Extension point |
|---|---|---|---|
| **Swipe, inside "For you" only** | swipe right | swipe left | `NewsReaderDetailFragment.onSwiped()` switch at :658-687 — branch on `idFolder == AI_FOR_YOU` **before** reading `SP_SWIPE_LEFT/RIGHT_ACTION` |
| **Fast actions, in the article reader** | new `fa_ai_up` | new `fa_ai_down` | `res/layout/widget_fastactions_detailview.xml` (currently `fa_star`, `fa_mark_as_read`, `fa_open_in_browser`); gated by existing `CB_SHOW_FAST_ACTIONS` |
| **Swipe, anywhere else (opt-in)** | new value `"4"` | new value `"5"` | append to `pref_general_swipe_action` / `_values` arrays, `res/values/strings.xml:167-178`; picker already exists at `res/xml/pref_general.xml:106-117` |

**Do not change the global swipe defaults** (star / read). Existing users' muscle memory is not ours to spend. The For-You folder overrides them locally because that list exists *for* generating decisions — that's its job, and a triage list where swipe means "mark read" is a wasted surface.

**Undo is mandatory and is a first-class veille action.** Every swipe fires a `Snackbar` with `UNDO`, 5 s (precedent: `NewsReaderListActivity.showSnackbarNewItems():655`, `NewsReaderDetailFragment:878`). Undo writes an `undo` decision row (append-only, BRIEF.md:59) and returns status to `queued`. It does **not** delete the original row — the disagreement history is the input to the learn loop.

**Storage:** separate AI SQLite DB (forced by `DevOpenHelper` table-drop, BRIEF.md:266-271). Key on `RssItem.fingerprint`, **not** `id` — ids are reassigned after a schema-version wipe, fingerprints are content-derived and survive it (they're already the app's dedupe key: `UpdateCurrentRssViewTask` injects `GROUP BY FINGERPRINT`, BRIEF.md:312).

### Is "opened + scrolled" a usable implicit positive?

**No.** Three reasons, in order of weight:

1. **It cannot produce a negative.** "Didn't open" is not "rejected" — the user only ever sees ~25 rows per page (`PageSize = 25`) and most articles are never *seen*, let alone judged. An implicit-positive-only design gives you one centroid, which is exactly veille's cold-start state where similarity is switched off entirely (BRIEF.md:35-36). You'd be shipping a permanently cold system.
2. **"Read" is already automated in this app.** `CB_MARK_AS_READ_WHILE_SCROLLING_STRING` and `CB_SYNC_WHEN_SCROLLED_TO_BOTTOM_STRING` exist; read state is generated by scrolling past things. Read is a hygiene state here, not an intent state.
3. **Opening is driven by the headline, taste by the substance.** Clickbait would train the centroid toward clickbait — a well-documented failure of implicit-only recommenders, and one the user has no lever to correct because they never explicitly said anything.

**Deferred, not rejected:** dwell ≥ 30 s in `NewsDetailActivity` on an AI-selected article, stored in a separate `weak_positive` column, used **only as a tiebreaker between equal `rank_score` values**, never fed into the centroid. Off in v1. *What would resolve it:* a 2-week dogfood logging both, then compare ranking quality (nDCG against subsequent explicit decisions) with dwell-in vs dwell-out. Ship it only if it wins.

## 2. THE NEW MENU ENTRY

### Decision: **ONE** entry, named **"For you"**.

`AI_FOR_YOU(-14)` added to `SPECIAL_FOLDERS`, `ListView/SubscriptionExpandableListAdapter.java:88`. Placed **first** in the drawer, above "Unread" (`mCategories.add(...)`, :377-380) — it is the intended default destination.

Two entries ("For you" + "Digest") is wrong: the item set is small (veille's `prefilter_top_k` = 60, and only those clearing threshold get selected — realistically 5-20/day). Splitting 12 items across two drawer rows makes both look abandoned. The digest is a *view* of the For-You set, so it lives inside it (§3).

Not named "AI", not named "Smart". "For you" is honest about what it is (a personalised subset) and doesn't promise correctness.

### Badge count
**Unread ∧ AI-selected.** `status = 'selected' AND READ_TEMP != 1`.

Every other badge in this drawer is an unread count (`getUnreadItemCountFeedFolder()`, called from `NotifyDataSetChangedAsyncTask.doInBackground():494`); breaking that convention on one row makes the drawer unreadable. Critically, this count **decays as you read** — a badge that only ever grows is ignored within a week. New `dbConn.getAiSelectedUnreadCount()` + a branch near :286 alongside the `ALL_DOWNLOADED_PODCASTS` case.

**Must exempt the row from the only-unread purge:** `NotifyDataSetChangedAsyncTask.onPostExecute():514-535` removes folder rows with no unread count. Copy the `ALL_DOWNLOADED_PODCASTS` exemption at :523 — otherwise "For you" silently vanishes from the drawer the moment you finish reading it, and the user concludes the feature broke.

### Sort order
`rank_score DESC, PUB_DATE DESC, _id DESC` — mirrors `domain/digests.py::create` (BRIEF.md:73).

**`SP_SORT_ORDER` is deliberately ignored for this folder.** It is a relevance list, not a timeline. State this loudly to eng so nobody wires the pref in "for consistency". The order is stamped into `CURRENT_RSS_ITEM_VIEW` by the existing two-step query (`getAllItemsIdsForFolderSQL()` new branch at `DatabaseConnectionOrm.java:607-635`; `UpdateCurrentRssViewTask.doInBackground():521-563`) — which means the AI DB must be `ATTACH`ed or the ordering materialised, an eng decision (BRIEF.md PART D#1), but the *product* requirement is: **order is fixed at list-build time and does not change while the user is scrolling.**

### Cold start (zero decisions)

Veille falls back to recency (BRIEF.md:35-36). **Recency is acceptable as content; it is not acceptable as presentation.** An unlabeled recency list under a "For you" header is worse than empty — the user believes the AI chose these, sees noise, and concludes the AI is bad. That's an unrecoverable first impression.

**Design:** the list *is* populated (top 60 most recent unread, veille's rule), but a **non-dismissible onboarding card sits at position 0**:

> **Learning what you like**
> Swipe right on articles worth your time, left on the rest.
> **3 of 10** ▓▓▓░░░░░░░
> [ Use my starred articles ]

Below the card, a section divider reading **"Most recent — not yet personalised"**. Honest, and it converts the degraded state into a task with a visible finish line.

**Warm-up threshold: 10 decisions total, with ≥3 of each polarity.** Below that we do not compute centroids and do not claim ranking. Veille has no such gate (any single decision builds a centroid) — but veille has an operator who understands the machine. A phone user given a ranking derived from one liked article sees randomness and uninstalls.
*Uncertainty:* 10/3 is a judgement call, not a measurement. *Resolves by:* during dogfood, compute Spearman ρ between consecutive rankings as decision count grows; set the gate where ρ plateaus.

### Empty states
Reuse `res/layout/empty_content_view.xml` (`@id/title` + `@id/description`). Four distinct states — **never one generic "nothing here"**:

| Condition | Title | Description |
|---|---|---|
| No model installed | **AI triage is off** | Download a model in Settings → AI to sort your feed by what matters to you. `[Set up]` |
| Warm, batch scored, nothing cleared the bar | **Nothing worth your time in this batch** | 47 new articles were scored. None matched your interests. They're all still in Unread. |
| All selected items read | **You're through For you** | The next batch arrives after the next sync. |
| Device unsupported | **This device can't run on-device AI** | For you needs 4 GB of RAM. Everything else works normally. `[Why?]` |

The second row is the important one: **always say where the articles went.** The single fastest way to lose trust is for a user to suspect the AI deleted their news.

## 3. THE DIGEST

### Decision: a **pinned card at the top of "For you"**, expandable to a full screen. Not a periodic screen. Not a notification by default.

A separate "Digest" destination gets opened twice and forgotten. A notification-first digest is an interruption budget we haven't earned in v1. The card is seen every time the user opens the app's default destination — zero cost to discover, zero cost to ignore.

Country→theme grouping is wrong on a phone (BRIEF.md:75): veille's country axis exists because a team watches several markets. One user, one market. **Collapse to theme only.**

### The card (`DigestCardViewHolder`, a new view type in `adapter/NewsListRecyclerAdapter.java`, position 0)

```
┌──────────────────────────────────────────────┐
│ DIGEST · Fri 1 Aug · 14 selected             │  overline, 11sp caps
│                                              │
│ Regulators moved on two fronts this week…    │  abstract, maxLines=3
│ …while three competitors shipped in the      │  ellipsize=end
│ same fortnight.                              │
│                                              │
│ [Regulation 5] [Competitors 4] [On-device 3] │  chips, tap = filter list below
│                              Read digest  →  │
└──────────────────────────────────────────────┘
```

- Abstract = `abstract.md` output, **3-5 sentences, device locale only**.
- Chips = top 3 themes by `−sum(rank_score)` (veille's theme-block ordering). Tapping a chip filters the list below it — this is the cheapest possible "grouping" on a phone and costs no new screen.
- Card is dismissible for the day (`X`); returns tomorrow.

### The full screen (`AiDigestActivity`)
1. Full abstract (3-5 sentences, no truncation).
2. **Theme sections**, ordered by `−sum(rank_score)`. Each item appears **once**, under `themes[0]` (veille's rule, BRIEF.md:76) — no article in two sections.
3. Per item: title, feed name + favicon, the why-line, score pill. Tap → `NewsDetailActivity`.
4. Footer: `Mark all as read` · `Share` (`ACTION_SEND` `text/plain`, Markdown body — reuses veille's export shape and the existing share intent code at `NewsReaderDetailFragment.java:672-681`).

### Cadence: **once per calendar day, generated lazily on first open.**
Trigger: user opens "For you", it's a new calendar day, and ≥5 items have been selected since the last digest. Then generate.

Not on every sync — sync can fire 8×/day (`ContentResolver.addPeriodicSync`, `SettingsFragment.setAccountSyncInterval():411-431`) and 8 abstracts/day is battery burned on a screen nobody opened. Lazy-on-open means we pay exactly one inference, and only when it will be read. While generating: the card renders immediately with the item count and theme chips (both computed from the DB, no inference), and a shimmer where the abstract goes. **The card never blocks on the LLM.**

Range semantics mirror veille exactly: items **selected since the last digest** (`decided_at`), not published since (BRIEF.md:74).

### Notification: opt-in, off by default.
One switch in Settings → AI: "Daily digest notification" + time picker (default 08:00). When on, generation becomes eager at that time *and only while charging* — this is the one case where we pre-compute. Reuse the existing notification path rather than inventing one (`OwnCloudSyncAdapter.updateNotification():232`). Notification text = first sentence of the abstract + "14 articles"; tap → `AiDigestActivity`.

## 4. PROGRESSIVE DISCLOSURE

**Two non-negotiable rules, stated first because everything else follows from them:**

1. **Nothing blocks.** The For-You list renders from the DB immediately, always. No full-screen spinner, ever. Inference never gates a screen. (`Engine.initialize()` alone is up to 10 s — BRIEF.md:393.)
2. **No silent AI.** BRIEF.md:204 makes "degrade gracefully" a code rule. The UX rule is stronger: **degrade *visibly*.** If the AI did not run, the folder says so, in one line, at the top. A user who can't tell whether the AI ran cannot tell whether it's working.

### The status strip — one line at the top of "For you", below the digest card

| Engine state | List shows | Strip | Row detail |
|---|---|---|---|
| No model | 60 most recent unread | **AI triage off** · `Set up` | plain rows |
| Downloading | 60 most recent unread | **Downloading Gemma 3 1B · 340/720 MB** + determinate bar | plain rows |
| Embedder only (LLM absent / too big for device) | **ranked by similarity** | **Ranking by similarity. Add a scoring model for scores and summaries.** · `Settings` | rank order only, no pill, no why-line |
| Scoring running | ranked, partially filled | **Scoring 23 of 60…** | scored rows get pill + why; pending rows show a shimmer bar where the why-line goes |
| Deferred (not charging / battery < 20% / thermal throttled) | last completed ranking | **Waiting for charger** · `Run now` | stale rows keep their old pills |
| Device too small | 60 most recent unread, permanently | **This device can't run on-device AI** · `Why?` | plain rows |
| Runtime failure (OOM, parse collapse) | last completed ranking | **Scoring failed** · `Retry` · `Try a smaller model` | unscored rows keep sim rank |

This strip **is** veille's degradation ladder rendered as UI. The mapping is 1:1: no embed → recency; no score → rank on sim alone; no enrich → keep the stage-2 why-lines (BRIEF.md:204).

### Row-level progressive fill
A row becomes visible as soon as it's **embedded** (it has a sim rank). Score pill and why-line fill in afterwards as the batch completes.

**Rows must not reorder while the list is on screen.** Re-ranking is applied only on pull-to-refresh or on re-entry to the folder. Content shifting under a scrolling thumb is the single most-hated failure mode of every AI feed; the existing `CURRENT_RSS_ITEM_VIEW` materialisation (`insertIntoRssCurrentViewTable`, BRIEF.md:309) makes this the *natural* implementation, so getting it right is free — but it must be written down or someone will "improve" it with a live re-sort.

### Model not downloaded yet
Never a blocking modal. First entry to "For you" shows the cold-start list plus a one-time bottom sheet: what it does, model size, "downloads once, then works offline, nothing leaves your phone". Two buttons: `Download (720 MB)` / `Not now`. On Wi-Fi-only by default. Download runs in the background with a notification; user can leave the app.

**Gated Gemma weights**: a 403 (BRIEF.md:450) must NOT surface as "download failed". It surfaces as: **"Google requires you to accept the Gemma licence"** + `Open in browser` + `I've accepted — retry`. Anything less and a large share of users are permanently blocked with an unactionable error.

### Device too small
Gate **before** the download button is ever tappable (the Gallery `ModelPicker` memory check, BRIEF.md:455). In Settings → AI, oversized models are listed but greyed with an inline reason: *"Needs 4 GB RAM · this device has 3 GB"*. Never let a user spend 2.5 GB of a metered connection to hit an OOM. If **no** model fits, "For you" still exists and still works as a chronological list — the feature degrades to zero AI without degrading to zero function.

## 5. THE "WHY"

### Decision: **keep it.** One line, For-You folder only, device locale only, from the scoring pass.

**Worth the tokens: yes, and it is close to free.** `why` (~20 tokens) is emitted inside the *same* JSON object as `score` and `themes`, in the *same* batched call (batch = 10, BRIEF.md:41-43). Removing it saves ~1.2k output tokens per 60-item sync against ~18k input tokens — an immaterial latency win. What it buys is the only mechanism by which the user can audit the ranking. On-device this matters **more** than in veille, not less: a 1B-4B model's judgement is less trustworthy than Haiku's, and the why-line is how the user catches it being wrong and immediately corrects it with "Less like this". Cut the why-line and the negative signal loses its trigger.

**Cut instead: the bilingual requirement.** Veille emits `why_fr` **and** `why_en` (BRIEF.md:149-151). On-device, emit **one** `why` in the device locale (BRIEF.md PART D#8). That halves output tokens on the highest-volume stage — a real saving, unlike cutting the why itself.

### Placement
`subscription_detail_list_item_headline_thumbnail.xml` is a **fixed `124dp`** row with a 3-line bold `@id/summary` (title), favicon, star, feed name, 88dp thumbnail. There is no room. **Do not modify it** — it's shared with Unread and every folder.

**New layout `ai_list_item.xml` + a new view-holder variant** alongside the 7 that already exist (`adapter/NewsListRecyclerAdapter.java`, base `adapter/RssItemViewHolder.java`), selected by `idFolder == AI_FOR_YOU` rather than by `sp_feed_list_layout`:

```
┌────────────────────────────────────────────────┐
│ Title, bold 17sp, maxLines=2      ┌──────────┐ │   ← was 3 lines
│                                   │  88dp    │ │
│ Why this matters, 13sp italic,    │  thumb   │ │   ← NEW, maxLines=2
│ colorOnSurfaceVariant, maxLines=2 └──────────┘ │      ellipsize=end
│ ⟨3⟩ ◉favicon  Feed name · 2 h ago              │   ← NEW score pill
└────────────────────────────────────────────────┘
```

- `minHeight=124dp`, height `wrap_content` (rows without a why-line don't grow).
- `@id/ai_score_pill`: 18dp circle, the digit 2 or 3, tinted by tier. Present **only** when a score exists. **Absent means absent** — never render a "0" or a placeholder for an article the model failed to parse. That row keeps its similarity rank and simply has no pill, exactly mirroring veille's `score=None` degrade (BRIEF.md:196-197). This is the visual encoding of "scoring must never lose an article".
- The star icon stays (`@id/star_imageview`) — starring is unaffected and orthogonal.
- Why-line does **not** appear in the article reader (`NewsDetailActivity`); the article is right there.

## 6. ACCEPTANCE CRITERIA

Executable on a device by QA. Build: `./gradlew :News-Android-App:assembleDevDebug`.

**Setup / cold start**
1. Fresh install, account synced, no model downloaded → drawer shows **For you** as the first row, above Unread, with a badge of `0`. Tapping it shows a list of the most recent unread articles, an onboarding card at position 0 reading "Learning what you like — 0 of 10", and a status strip "AI triage off · Set up".
2. Tap `Set up` → Settings → AI. Tap a model whose size exceeds free storage → download button is disabled with an inline reason. Tap a model exceeding device RAM → greyed, reason names both required and available RAM.
3. Start a download, background the app, return → progress persisted and still advancing. Kill the app mid-download, relaunch → status shows partially-downloaded and offers Resume, not Restart.
4. With a Gemma model not yet licence-accepted, start download → error reads "Google requires you to accept the Gemma licence" with `Open in browser` and `I've accepted — retry`. It does **not** read "download failed".
5. In Settings → AI, tap **Use my starred articles** with ≥10 starred items → onboarding counter jumps to ≥10 and the list re-ranks on next entry to the folder.

**Signal**
6. In **For you**, swipe an article right → Snackbar "More like this · UNDO"; the row leaves the list; the onboarding counter increments by 1.
7. Tap `UNDO` within 5 s → the row returns to its original position, the counter decrements, and the article's status is back to unrated. Re-swiping it works normally.
8. Swipe left → Snackbar "Less like this · UNDO", same behaviour, counter increments.
9. In **Unread**, with default settings, swipe right → the article is **starred** (unchanged legacy behaviour). Nothing AI-related fires.
10. Settings → General → "Action when swiping right" now lists "More like this" and "Less like this". Select "More like this", return to **Unread**, swipe right → AI positive fires, article is **not** starred.
11. Star an article in Unread → the AI decision count does **not** change. Starring is not a taste signal.
12. Open an article from For you, scroll to the bottom, back out → the AI decision count does **not** change (no implicit positive in v1).
13. Open an article → fast-action bar shows thumb-up and thumb-down alongside star and mark-as-read. Tap thumb-up → toast/Snackbar confirms, decision count increments.
14. Uninstall-free schema wipe simulation (bump the greenDAO schema version, reinstall over) → RSS cache is rebuilt from the server **and the AI decision count is preserved** (fingerprint-keyed, separate DB).

**Ranking & the list**
15. With ≥10 decisions (≥3 each polarity) and a model installed, run a sync → the onboarding card disappears, the "Most recent — not yet personalised" divider disappears, and rows carry a score pill and a one-line why.
16. The For-You order is **not** affected by Settings → General → Sort Order. Flip it to Old→New → Unread reverses, For you does not.
17. While a scoring pass is running, scroll the For-You list → **no row changes position**. Pull to refresh → order updates in one step.
18. Force a scoring failure (airplane-mode-equivalent: delete the model file mid-pass) → the strip reads "Scoring failed · Retry"; the list still renders, ordered by similarity; **no article has disappeared** — every item is still findable in Unread.
19. Set the device to a state where the model cannot load (low-memory device or manually corrupted model) → For you falls back to the recency list, the strip states the reason, and every other part of the app (Unread, Starred, folders, sync, podcasts) behaves identically to the upstream build.
20. Read every article in For you → the drawer row **remains visible** with a badge of `0` even with "Show only unread" enabled; the list shows "You're through For you".
21. Run a sync where nothing clears the threshold → For you shows "Nothing worth your time in this batch — N new articles were scored…" and those N articles are all present in Unread.

**Digest**
22. On a day with ≥5 newly-selected items, open For you → the digest card renders **immediately** with date, count and theme chips; the abstract area shows a shimmer and then fills. The list below is scrollable throughout — the card never blocks it.
23. Tap a theme chip → the list below filters to that theme; the chip shows selected state; tapping again clears.
24. Tap "Read digest" → full screen, abstract in full, theme sections ordered by aggregate score. **No article appears in two sections.** Tap an item → article reader.
25. Reopen For you later the same day → the same digest (not regenerated — verify by absence of a second inference, e.g. logcat or a debug counter).
26. Cross midnight, sync in ≥5 new selections, reopen → a new digest for the new day.
27. Dismiss the digest card with `X` → gone for the day, returns the next day.
28. Share the digest → the share sheet receives Markdown text containing the abstract and every item grouped by theme.
29. "Daily digest notification" is **off** on a fresh install. Turn it on with time 08:00, leave the device on charge overnight → one notification at ~08:00; tapping it opens the digest screen.

**Non-regression**
30. With no AI model installed and the AI feature never touched, every screen, sync, badge count and swipe in the app behaves identically to the upstream build. `./gradlew detekt spotlessCheck lint test` all pass.

## OPEN / UNCERTAIN (flagged for other agents)

- **Warm-up threshold 10 decisions (≥3 each).** A product guess, not a measurement. Resolve with a dogfood ranking-stability measurement, not by argument.
- **Digest ≥5-item trigger.** Guess. Resolve by observing the actual daily selected-item distribution during dogfood; if the median day yields 3, the threshold is wrong and the digest becomes weekly.
- **Ordering across two SQLite DBs** (`ATTACH` vs denormalise into `CURRENT_RSS_ITEM_VIEW`) is an eng decision (BRIEF.md PART D#1). The product constraints on it are only: order is stamped at list-build time, and it must survive a greenDAO wipe.
- **Deferred: dwell-time weak positive.** Explicitly out of v1; ship criterion stated in §1.
- **Rubric on a phone** (BRIEF.md PART D#5) is deliberately not designed here — v1 ships centroids only, no user-visible rubric, no approval step. The why-line is the user's window into the model's reasoning; a hand-editable rubric is a v2 feature and needs its own spec.
